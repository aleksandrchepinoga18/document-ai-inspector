# Техническое задание: Document AI Inspector — MVP 

**Статус:** демопроект на 3 дня; не промышленная система. **Среда:** Windows 10/11, Git Bash, Docker Desktop, Ollama на хосте. **Основное ограничение:** никаких реальных конфиденциальных документов в облачных LLM.

## 1. Цель и границы

Принимать DOCX, детерминированно проверять оформление по конфигурируемому профилю, выявлять с помощью LLM смысловые противоречия, формировать объяснимые замечания, применять **только разрешённые безопасные форматные** изменения, сохранять оригинал, выдавать DOCX, PDF-предпросмотр и машинно-читаемый отчёт.

Это **не** универсальная экспертиза любых документов и **не** полностью автономный редактор. Без RAG, Qdrant, MCP, LangGraph, fine-tuning, Kubernetes, полноценного плагина Яндекс Трекера и Go-backend. Векторы и агенты не требуются.

## 2. Стек

- Python 3.12; FastAPI, Pydantic v2, pydantic-settings; Streamlit.
- `python-docx` + `lxml` для чтения и адресных правок OOXML; `Docling` для отдельного смыслового представления, **без потери связи с исходными ID элементов**; при проблеме выравнивания элементов — fallback на собственное извлечение через `python-docx`.
- LibreOffice CLI для PDF и PyMuPDF для просмотра/проверок; полноценный pixel-diff OpenCV вне MVP.
- OpenAI Python SDK с адаптерами: локальная Ollama/Qwen; Yandex AI Studio (ключ и идентификатор каталога через `.env`, API и имя модели конфигурируемые); vLLM через совместимый API **только адаптер, без обязательного GPU-развёртывания**.
- pytest, pytest-cov; MLflow Tracking Server; Docker Compose.

Версии зависимостей должны быть закреплены в lock/requirements с воспроизводимой установкой. Ни одно конкретное облачное имя модели не должно быть захардкожено в бизнес-логике.

## 4. Контракт работы с документом

- Принимать только DOCX; проверять MIME/расширение, ZIP, необходимые OOXML-части, лимит размера, число ZIP-элементов и отношение распаковки; исключать path traversal; не выполнять макросы и внешние ссылки. Ограничить время обработки. Неподдерживаемые/повреждённые файлы отклонять с внятной ошибкой.
- Оригинал хранить неизменным; каждому заданию присвоить UUID, каждому извлечённому элементу — воспроизводимый ID **в пределах конкретной версии файла** (например, xpath + порядковый индекс); фиксировать mapping ID → исходный OOXML-узел.
- Поддержать в MVP абзацы, обычные таблицы, заголовки, стили и свойства текста. Явно маркировать объекты/случаи, для которых безопасная правка не реализована: поля, формулы OMML, сноски, сложные объединённые таблицы, track changes и др.
- Формальные правила хранить в версии профиля (JSON/YAML), а не в промпте: семейство и размер шрифта, первая строка, выравнивание, заголовки, обязательные разделы, подписи таблиц. Учитывать наследование свойств из стилей; `None` в python-docx не трактовать как «ошибка» без вычисления эффективного значения либо помечать «не определено».
- Унифицированное замечание: `id`, `rule_id`, `category`, `severity`, `element_id/locations`, `evidence`, `actual`, `expected`, `source` (`rule|llm`), `suggestion`, `auto_fix_allowed`, `status`. Схемы через Pydantic.

## 5. LLM-анализ

- Единый `LLMProvider` с `analyze()` и конфигурацией base URL, модели, auth, timeout, retries, температуры и лимита вывода.
- Ollama: локальная модель через OpenAI-compatible endpoint; при использовании Docker и Ollama на Windows-хосте — `host.docker.internal`.
- Yandex AI Studio: подключение через действующий документированный API; только **по явному выбору** пользователя, с демонстрационными синтетическими данными. Ошибки авторизации и квот показывать явно; ключи не логировать.
- vLLM: реализовать совместимый адаптер с mock-тестами; не утверждать, что запуск на GPU состоялся без фактической проверки.
- Цель модели: обнаружить противоречие между фрагментами и вернуть типизированные замечания с цитируемыми фрагментами/ID. Проверять ссылки на реально существующие фрагменты и JSON/Pydantic-схему. Не считать ответ LLM эталоном и не давать ей изменять DOCX.
- При недоступной LLM детерминированная проверка должна продолжать работать.

## 6. Исправления, валидация, рендеринг

- Автоматически изменять только явно разрешённые свойства поддерживаемых элементов (например, размер шрифта в стандартном абзаце). Не менять числа, текстовые факты, формулы, изображения или содержимое таблиц автоматически.
- Работать в копии исходного DOCX; сохранять checksum оригинала; проверять неизменность текста, числа элементов, таблиц, embedded media, формул, связей и неразрешённых OOXML-частей. Не требовать побайтового совпадения всего ZIP: меняются разрешённые XML-части/метаданные.
- При провале инвариантов файл с правками не публиковать; вернуть исходник и ошибку. Каждую правку протоколировать.
- LibreOffice выполнять headless с timeout и изоляцией временных директорий; рендерить PDF, проверять открываемость/страницы. **PDF-конвертация и близость числа страниц не доказывают отсутствие всех дефектов верстки.**

## 7. API и UI

- `GET /health` → JSON статуса.
- `POST /documents/check` (multipart DOCX, профиль, провайдер, включение LLM и auto-fix) → UUID задания и результат/ссылки; для MVP допустим синхронный запуск с ограничением времени.
- `GET /documents/{id}/report` → Pydantic/JSON замечания и метрики выполнения.
- `GET /documents/{id}/download` → DOCX при успешной проверке инвариантов.
- `GET /documents/{id}/preview` → PDF, если рендер успешен.
- Streamlit должен использовать **реальный FastAPI**, а не собственную дублирующую логику и не фиктивные результаты. Выбор провайдера, загрузка, таблица замечаний, скачивание результатов.

## 8. Датасет и оценка качества LLM

- Создать **минимум 20–30 отдельных синтетических кейсов**: положительные (с ошибкой), отрицательные (без ошибки) и неоднозначные; указать правду как `(document_id, location(s), error_type, evidence)`.
- Для LLM проводить оценку именно **смысловых ошибок**, отдельно от формального rules engine. Одинаковые версии набора, промпта, критериев сопоставления и параметры генерации для сравниваемых моделей.
- Определить правило матчирования: одинаковый тип + подходящее место/пара разделов и подтверждение фрагментом. Один эталон сопоставляется не более чем одному предсказанию. Подсчитывать TP, FP, FN, precision, recall, F1; TN не нужен для event-level обнаружения, но отрицательные кейсы обязательны для FP.
- Дополнительно считать JSON-valid rate, долю ответов со ссылками на существующие фрагменты, latency mean/p95, количество ошибок API. На маленьком синтетическом наборе показатели **не являются доказательством качества на реальных документах**.
- `evaluation/benchmark.py` — ручной CLI-запуск. Отдельный режим `--dry-run`/mock не должен создавать мнимые результаты реальных моделей. Платные вызовы только с явным флагом и выбранным провайдером.

## 9. MLflow

- Локальный MLflow Tracking Server с постоянным backend store и хранилищем артефактов (для MVP SQLite + локальный volume, если поддерживается установленной версией; пути/права протестировать). Доступ по `http://localhost:5000` только локально.
- Логировать: провайдер/модель, версии промпта/набора, настройки генерации, TP/FP/FN, P/R/F1, JSON-valid rate, latency mean/p95, количество кейсов и обезличенный CSV/JSON с результатами.
- Никаких ключей, токенов или конфиденциальных DOCX в артефактах. Обычная проверка документов не должна зависеть от доступности MLflow.

## 10. Тесты и ручное выполнение

- pytest unit: parser, rules, editor, OOXML-инварианты, схемы, метрики, адаптеры с mocks; pytest integration: API → проверка → исправление → экспорт, включая негативные DOCX.
- Реальные сетевые интеграционные тесты Ollama/YandexGPT маркировать `external`; **исключить из обычного `pytest`**. В стандартном CI не должно быть платных API-вызовов.
- Docker Compose сервисы с именами `api`, `ui`, `mlflow`; в контейнере `api` должны быть dev-зависимости, тесты и исходники, чтобы работали `docker compose exec api python -m pytest -v` и `docker compose exec api python -m pytest --cov=backend --cov-report=term-missing`.
- В `README.md` дать рабочие команды **для Git Bash**, проверенные в доступной среде: `docker compose up -d --build`, `docker compose ps`, `curl http://localhost:8000/health`, `docker compose exec api python -m pytest -v`, `docker compose logs -f api`, `docker compose down`. Для MLflow — `http://localhost:5000`, для Streamlit — `http://localhost:8501`. Если сервис не стартует, предоставить конкретную диагностическую последовательность.
- Секреты хранить в `.env`, с примером `.env.example`; `gitignore` для `.env`, результатов, DOCX и artifacts. Проверить, что сборка не копирует секреты в образ.

## 11. Этапы приёмки — единственный порядок реализации

1. **Инфраструктура:** каркас, FastAPI `/health`, Streamlit placeholder, Compose, MLflow, тесты smoke.
2. **Документы:** парсер, профили правил, проверка, синтетические примеры, API и unit-тесты.
3. **Редактор:** безопасная правка, OOXML-инварианты, LibreOffice/PDF, скачивание.
4. **LLM:** Ollama + Yandex AI Studio, общий адаптер + vLLM mock, структурированные замечания; opt-in реальные вызовы.
5. **Evaluation:** эталонные кейсы, CLI бенчмарк, метрики, MLflow.
6. **UI и полировка:** Streamlit → FastAPI, сквозные тесты, README, короткое демо.

На каждом этапе Codex изменяет только относящиеся к этапу файлы и предоставляет: список файлов, что реально реализовано, ограничения, **команды ручной проверки через Git Bash и ожидаемый результат**. Пользователь сам запускает команды и передаёт лог. Без явного подтверждения следующий этап не начинать. Не писать «всё работает», если не проверялось.

## 12. Приёмка MVP

На синтетическом DOCX пользователь может найти формальные ошибки, увидеть смысловое замечание при доступной LLM, скачать отдельную безопасно исправленную версию и отчёт; исходник не изменяется; pytest проходит вручную; Compose запускает API/UI/MLflow; реальный бенчмарк можно запустить вручную и увидеть его в MLflow. Отсутствие GPU, API-ключа Yandex или доступа к облаку не блокирует автономный режим и unit-тесты.
