# Бенчмарк этапа 5

Запускать из корня: `python -m evaluation.benchmark`. Реальные вызовы выполняются
только вручную при явном `--provider`; Yandex дополнительно требует `--allow-paid`.
Набор встроенный: CLI не принимает пользовательские DOCX или произвольные датасеты.

`datasets/synthetic-v1.json` содержит 24 отдельных документа: 12 положительных,
8 отрицательных, 4 неоднозначных. Тексты и эталонные цитаты заданы вручную,
без генерации разметки моделью. Это разметка автора демопроекта, без независимого
экспертного аудита. Каждый документ содержит два раздела; генератор нормализует
ZIP timestamps, сохраняет стабильные ID парсера и проверяет привязку разметки.
Эталон: document_id + error_type + references(element_id, quote).
Изменение текста/разметки требует новой версии набора.

Текущее сопоставление `type-exact-locations-terminal-period-v2`: одинаковый тип
`contradiction`, одинаковое множество ID и наличие полной эталонной цитаты в
цитате предсказания на каждом ID после удаления внешних пробелов и одной конечной
точки. Числа, отрицания, условия, внутренняя пунктуация и многоточия сохраняются.
Старый `type-exact-locations-evidence-v1` доступен для воспроизведения baseline
и требовал совпадения также конечной точки. Порядок ссылок не важен.
Используется максимальное паросочетание;
один эталон и одно предсказание участвуют максимум в одной паре. Лишние замечания
дают FP, пропущенные эталоны — FN. Корректная, но слишком короткая цитата может
не пройти этот строгий критерий; результаты следует просматривать вместе с evidence.
Обнаруженные моделью ошибки оформления не оцениваются: rules engine не запускается.

TP/FP/FN суммируются по 20 однозначным документам; precision, recall и F1 считаются
micro, нулевой знаменатель даёт 0. TN не считается. Неоднозначные документы
исключены из качества, их число и количество замечаний выведены отдельно.
Ошибки/таймауты не исключают документ: его эталоны остаются FN. Невалидный ответ
целиком отклоняется по контракту этапа 4; отброшенные замечания не считаются FP.

JSON-valid rate означает соответствие JSON **и Pydantic-схеме**; references-valid
rate — прохождение всех проверок ссылок/разделов/дословных цитат. Знаменатель обоих
показателей — все 24 кейса, включая неоднозначные и сбои. Валидный пустой ответ
проходит обе проверки. Mean/p95 включают все кейсы; p95 — nearest rank
`ceil(0.95*N)`. В реальном режиме latency включает запуск worker и парсинг,
в mock — только анализатор; эти задержки нельзя сравнивать между режимами.

API errors — число кейсов с ошибкой соединения, HTTP, авторизации, квоты или
таймаутом. Это не число отдельных неудачных HTTP-попыток: повторения отражены
в attempts, а после убийства worker их число может быть неизвестно.
`failed_case_count` включает также ошибки схемы, цитат и worker.

В `metrics_version=event-quality-validation-breakdown-v2` дополнительно считаются
`validation_error_count`, `evidence_error_count`, `reference_error_count`,
`json_error_count`, ошибки валидации по каждому kind,
`failed_negative_case_count`, `negative_false_positive_case_count`,
`successful_empty_case_count`. Успешный пустой ответ и отклонённый ответ
не смешиваются. На отрицательном кейсе сбой валидации по-прежнему не является
принятым FP; его показывает отдельный счётчик. Чистый event-level F1 не описывает
всех ошибок модели и должен читаться вместе с этими показателями.

Новые cases содержат `response_issue_count` (число issues в валидном по схеме
ответе), `discarded_issue_count` (весь ответ при отказе grounding) и
`validation_diagnostics` — координаты и причина **первой** ошибки без текста/ID
из отклонённого ответа. Причины: duplicate_id, unknown_id, same_section,
uninformative_quote, quote_not_found. Строгое дословное сравнение валидатора
не изменено; нормализация matcher не позволяет принять выдуманную цитату.

`observed_discarded_issue_count` суммирует только известные значения;
`discard_count_observed_case_count` задаёт покрытие. Аналогично
`issue_count_observed_case_count`, `observed_nonempty_response_case_count` и
`observed_nonempty_references_valid_case_count` разделяют непустые ответы и покрытие.
Для старых runs новые поля неизвестны, а не равны нулю; нулевые observed-счётчики
при нулевом покрытии не означают отсутствие отброшенных issues.

Каждый запуск создаёт отдельный `results/benchmarks/{real|mock}-UUID`:

- `summary.json`: параметры, метрики, ограничения.
- `cases.json`, `cases.csv`: статусы и счётчики по документам, ID и проверенные цитаты.
- `manifest.json`: синтетические тексты, эталоны, хеши DOCX и версии.
- `tracking.json`: ID MLflow run либо безопасный код отказа при включённом tracking.

MLflow получает только первые четыре файла. Не сохраняются ключи, URL провайдеров,
исходные ответы моделей, объяснения и DOCX. Предсказанные цитаты сохраняются лишь
после проверки их наличия в фиксированном синтетическом тексте.
Mock использует пустой ответ через MockTransport, независимо от эталона: ожидается
TP=0, FP=0, FN=12. Его эксперимент `semantic-benchmark-mock` отделён от реального
`semantic-benchmark`; mode/provider/model явно указывают mock.

Код возврата CLI: 0 — все кейсы и выбранный tracking выполнены; 1 — результаты
записаны, но есть сбои кейсов или MLflow; 2 — неверный выбор/конфигурация либо сбой
подготовки. При недоступном MLflow локальные результаты сохраняются; используйте
`--no-mlflow` для автономного запуска. Проверка документов API не вызывает MLflow.

Для сравнения моделей сверяйте dataset/prompt hashes, matching/generator versions,
версии пакетов и все `llm_*` настройки в summary. Температура 0 и одинаковые
параметры не гарантируют побитовую детерминированность инференса. На сервере модели
нужно отдельно фиксировать веса и runtime; имя модели может быть изменяемым alias.
Небольшой синтетический набор не доказывает качество на реальных документах.

Команды Docker/Git Bash и статус проверки приведены в корневом README.

## Офлайн-анализ сохранённого baseline

`evaluation.analyze_run` воспроизводит v1 и отдельно пересчитывает v2 по уже
принятым цитатам. Он проверяет hash датасета, соответствие manifest, цитаты,
уникальность ID и исходные метрики. Провайдеры и MLflow не вызываются.
Исходный каталог защищён от записи результата в него; выходной файл должен быть
новым. Отклонённые цитаты старого run восстановить невозможно.

```bash
AUDIT_FILE="results/benchmark-analysis/ollama-audit-$(date +%Y%m%d-%H%M%S)-$RANDOM.json"
.venv312/Scripts/python.exe -m evaluation.analyze_run --run-dir results/benchmarks/real-7d083fee55ad4e90ae91595cfb0a91fc --output "$AUDIT_FILE"
```

Подробный [разбор Ollama](reports/ollama-stage5-analysis.md) и
[предложения для отдельного prompt v2](prompts/contradictions-v2-proposal.md).
